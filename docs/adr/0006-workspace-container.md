# 0006. One ItemView leaf, N xterm instances multiplexed via vertical side-tab selector

- **Status:** Accepted
- **Date:** 2026-04-17

## Context

Today each terminal is its own `ItemView` leaf under `rootSplit`. When the user opens two terminals, `BottomDock.openLeaf` calls `workspace.createLeafInParent(rootSplit, ...)` twice, so Obsidian treats the two terminals as peers of any markdown leaf in the same row. That pattern works but bleeds out at the edges: there is no tab strip on the dock, nothing stops Obsidian's leaf-picker heuristic from reusing a terminal leaf for a markdown open, and the "New terminal" `+` affordance lives awkwardly in each view header instead of on the container.

FI-014 in `specs/anvil/future-ideas-backlog.md` frames the umbrella goal — give the terminal native chrome with a tab strip, a drag handle, a close X, and geometry that survives close/reopen. The Phase 2 spike for FI-014 had to pick a container shape before Phase 3 can wire any of that up. The `docs/ORIENTATION.md` / meta-plan constrains the shape: the dock is a single location, the contents are homogeneous (only terminals), and the surrounding e2e suite at `tests/e2e/tab-isolation.e2e.ts:162–255` locks in the property that notes must not land inside the terminal container.

Four ranked candidates were on the table before the research pass: (R1) custom `WorkspaceParent` subclass, (R2) monkey-patched `WorkspaceTabs`, (R3) one `ItemView` leaf multiplexing N xterms in its own DOM, (R4) N peer `ItemView` leaves with a synthesized chrome overlay. The Phase 2 prior-art research note `Programming/Tabbed Containers with Content Isolation - Prior Art.md` (vault) rejected R1/R2/R4 as structurally unable to close Obsidian's multi-leaf attack surfaces. R1 requires an extension point Obsidian does not expose; R2 requires coercing markdown opens back to the terminal view via a distinguishing file marker, and terminals have no backing file; R4 cannot isolate the peer leaves from `workspace.openLinkText`. VS Code's integrated terminal panel — a single workbench Part owning its own DnD controller, tab list, and typed editor input — was the prior art. VS Code's isolation is not available to a plugin (we cannot add Parts to Obsidian), but the *shape* — one DOM subtree owned by the plugin, tabs drawn by the plugin rather than by the host, homogeneous content — is portable.

The spike prototype at `specs/anvil/pane-chrome-and-picker/phase-2-prototype/` implemented R3 against the pinned Obsidian 1.12.7 binary, with a vertical side-tab selector and a real `pty-server`-backed shell per tab. R8a–R8d (see below) exercise the three `openLinkText` modes and synthetic HTML5 drop against the container; R8e exercises a third-party `setViewState({type:"markdown"})` call against the container leaf.

## Decision

Adopt **Rank 3**. One `ItemView` subclass — the container — owns the terminal dock's DOM subtree and manages an internal list of tabs. Tab switching toggles `display: none` on sibling xterm mount points; the xterm instances and their PTY backends stay live across switches. The container is registered with a dedicated view type and mounted via the existing `getDock()` seam in `src/main.ts:159–170`.

**Concrete API surfaces Phase 3 will depend on:**

- **`ItemView` subclass + view type string.** New class (`TerminalContainerView` or similar) extending `ItemView`, registered with a stable view type (`"anvil-terminal-container-view"`). `getViewType()`, `getDisplayText()`, `getIcon()` are the `ItemView` contract. `onOpen()` builds the DOM (`this.containerEl.children[1]`), `onClose()` disposes every tab's xterm + PTY.
- **`View.navigation = false`.** Public property documented since Obsidian 0.15.1. Set on the container class to signal Obsidian's leaf-picker heuristic that this leaf is not a navigation target. This is the **load-bearing R8a mitigation** — without it, default-mode `openLinkText` reuses the container leaf for markdown opens. Proven by the Part 2 AC6 bite-check: flipping to `true` turns R8a red.
- **`Workspace.createLeafInParent(rootSplit, index)` placement.** Not in `obsidian.d.ts`'s public surface; the main plugin's `src/dock/bottom-dock.ts:44–77` already uses this pattern, feature-detected per that file's idiom. Places the container leaf as a direct child of `rootSplit` with **no `WorkspaceTabs` wrapper**. This is the **load-bearing R8b/c/d mitigation** — with no tab-group wrapper, `openLinkText("tab")` has no adjacent slot to land a sibling note into, and `openLinkText("split")` must create a new split rather than reusing our group. Proven by the Part 2 AC6 bite-check: the sibling-into failure was the first thing observed before the prototype was corrected.
- **`Workspace.registerView`.** Already used by `src/main.ts:44–47` for the current `TerminalView`; the container view registers alongside. The current `TerminalView` + `TERMINAL_VIEW_TYPE` stays registered for Phase 3's migration window, then is removed once `openTerminalWithSpec` targets the container exclusively.
- **Internal DOM multiplexing.** Each tab owns a `contentEl` under the container's content area. xterm mount is at `host.mount(contentEl)` per the existing `src/terminal/xterm-host.ts:39` pattern. Switching tabs sets `display` on the sibling `contentEl`s and calls `host.fit()` + `host.focus()` on the newly-visible one inside `requestAnimationFrame`.

**`WorkspaceLeaf.setPinned(true)` was tried and dropped.** The Part 1 prototype called `setPinned(true)` on the container leaf as belt-and-suspenders behind `navigation = false`. The Part 2 AC6 diagnostic showed it was redundant: with `navigation = false` in place, removing the `setPinned` call left all five R8 probes green. Dropping it removes one undocumented-API dependency from the final design. Future maintainers who reach for `setPinned` as an isolation lever should check the bite-check history before adding it back.

**Feature-detect predicates (per R4 / `src/dock/bottom-dock.ts:44–63`):**

- `typeof workspace.createLeafInParent === "function"` — predicate for the placement path. If absent (older Obsidian), fall back to `workspace.getLeaf("split", "horizontal")`. That fallback functions, but the container leaf lands inside a `WorkspaceTabs` wrapper, which **reopens R8b/c/d**. The container still works for its primary purpose (multiplexed terminals) — it just loses the sibling-into protection. Phase 3 should surface a one-time console warning when it hits the fallback path.
- `View.navigation` is documented since Obsidian 0.15.1 and `manifest.json` pins `minAppVersion` to `1.5.0`, so the property is guaranteed present. No runtime feature-detect needed.

**FI-012 relationship: Independent.** FI-012 (wrap-and-dock — avoid the rootSplit flatten on dock open) is a concern about how the dock leaf is *placed* into `rootSplit`. This ADR is about what's *inside* that leaf. The two solve different problems. FI-012's own note recommends sequencing alongside FI-014 because both touch rootSplit structure, and that recommendation still holds — Phase 3 should consider both together — but Rank 3 does not subsume FI-012 and can ship without it. Deciding FI-012 stays in the backlog.

**Why no fallback option.** The Phase 2 spec locked in that if Rank 3 failed an R8 probe un-mitigably, FI-014 defers rather than falling back to another rank. The prior-art research exhausted the field: R1/R2/R4 do not close the attack surfaces, and no fifth candidate is on the table. If future Obsidian releases break any API this ADR relies on, the migration is to re-run the spike, not to retreat to a rejected rank.

## Consequences

**Easier:**

- Foreign content cannot land inside the container via `openLinkText`. Two load-bearing properties close the surface: (a) `view.navigation = false` tells Obsidian's leaf picker to skip the container for default-mode opens (R8a); (b) direct placement under `rootSplit` without a `WorkspaceTabs` wrapper leaves `openLinkText("tab")` and `"split"` modes no sibling slot to grab (R8b, R8c). The synthetic-drop surface (R8d) is closed by the container having no drop handler. The existing isolation asserted by `tests/e2e/tab-isolation.e2e.ts:162–255` carries over — the current `TerminalView` already benefits from the placement property via `BottomDock`, so R8b/c/d carry over unchanged; `navigation = false` is what's new and closes R8a.
- Terminal state survives tab switches by construction. xterm instances are never disposed on switch — only hidden with `display: none`. The PTY keeps running, scrollback persists, cursor position persists, foreground processes continue. This is the property the single-leaf model buys; the multi-leaf model can't provide it without a separate state-preservation layer.
- Chrome is the plugin's to draw. The tab strip, the `+` affordance, the close X, the right-click menu live on DOM the plugin owns. No fighting with Obsidian's view-header layout, no magic numbers against Obsidian's status overlay (FI-014's stated reason for wanting native chrome).
- Phase 3's integration at `src/main.ts:159–170` becomes: `getDock()` returns the container leaf (creating it if absent), and `openTerminalWithSpec` calls a method on the container view (`addTab(spec)`) instead of `dock.openLeaf() + setViewState`. The existing `BottomDock` becomes single-leaf, simpler. `reconcileDock`'s leaf-counting loop collapses to "is the container open? yes/no."
- VS Code-shaped mental model. The container is the plugin's "workbench panel." Tabs are the plugin's tabs, not Obsidian's tabs. Users already have that shape from every code editor they've used.

**Harder:**

- Third-party `leaf.setViewState({type:"markdown"})` on the container leaf is **not blocked**. `view.navigation = false` influences Obsidian's *heuristic* picker — it does not intercept an explicit `setViewState` call from another plugin. The research note was explicit: "setPinned... does not block explicit `openFile(targetLeaf, ...)` calls, `setViewState`, or drag-drop onto the tab header"; and while we dropped `setPinned`, the same is true of `navigation`. R8e documents this as a residual risk; the plugin chooses not to adopt the monkey-patching pattern (Kanban/Excalidraw rely on a file-extension or frontmatter marker, which terminals do not have) and accepts that a specifically adversarial third-party plugin targeting our view type can destroy the container. Realistic exposure is narrow — third-party plugins rarely call `setViewState` on leaves they don't own — but it is not zero. If it bites in the wild, the recovery path is to detect the clobber via `workspace.on("layout-change")` and re-create the container leaf, not to prevent it. User-facing framing, symptom list, and known-risky plugins live in [docs/explanations/third-party-plugin-compatibility.md](../explanations/third-party-plugin-compatibility.md).
- Layout persistence of per-tab state was initially in scope (Phase 3 AC8) but was dropped post-merge. Obsidian's layout-save/restore serializes leaves but not our tabs; the original plan was a `{ tabs: Array<{shell, cwd, shellArgs}> }` serializer in `getState()`/`setState()`. During Phase 3 dogfooding, the ordering required to satisfy that AC (fire-and-forget `backend.start` so `changeLayout()` sees all tabs synchronously) introduced a zsh `PROMPT_EOL_MARK` regression on every prompt. The feature also didn't match user expectations — VS Code doesn't restore terminal sessions across restart — and our PTY architecture can't meaningfully preserve shells across any view-reconstruction boundary (popout / workspace-plugin / restart all tear down the renderer-bound `pty-server`). Shipped behaviour: on view reconstruction, the container opens with one blank terminal (if it was open before closing) or nothing (if it wasn't). Superseded by the "Post-merge rescope" section of `specs/anvil/pane-chrome-and-picker/phase-3-workspace-container-completion-report.md`. FI-005 (cross-session scrollback) remains the larger related problem; this ADR no longer demands any tab-state round-trip.
- The view header's `+` action and the tab strip's `+` are duplicated affordances. The prototype kept both. Phase 3 will have to pick a canonical location (the tab strip is the VS Code-natural place; the view header action is the Obsidian-natural place). Not a blocking decision; flagged so it isn't re-litigated at implementation time.
- Drag-drop on tab headers is out of scope for this ADR. Dragging a file onto the tab strip is a separate surface with its own expected semantics (VS Code sends the file path as `cd <path>` text to the active terminal). Phase 3 can implement that by attaching a `dragover` / `drop` listener to the tab strip DOM; the container ADR names the surface but does not commit to the behavior.
- `WorkspaceTabs` is not the mechanism. The ADR deliberately does not claim a tab group or touch `WorkspaceParent` surface. That limit is what keeps us inside sanctioned API — the tradeoff is we don't get Obsidian's native tab drawing, dragging between tab groups, or "merge to window" behavior. FI-014's note that native chrome gets those for free does not apply here; what we get is isolation and state preservation, not Obsidian-native tab ergonomics.

**Reversible?** Mostly. The ADR's decision is localized to a new view class + a refactor of `getDock()`'s contract. If Obsidian ships a typed-tab-group API (the Jan 2026 forum thread documents the ask), this ADR would be superseded by a new one that migrates to it — the container view becomes the migration point, not a plugin-wide rewrite. What is not reversible without a visible regression is the UX contract that tabs survive switches with state intact; a future approach that disposes xterm state on switch would regress.

**R8 verification status.** Phase 2 Part 2 automated all five probes as mocha/wdio tests under a dedicated `wdio.proto.conf.mts` that loads the built prototype plugin into the pinned Obsidian 1.12.7 test binary. Results:

- **R8a** `openLinkText(base, "", false)` — PASS. Note opens outside the container; container stays visible.
- **R8b** `openLinkText(base, "", "tab")` — PASS. Note opens in a separate tab group; the container has no `WorkspaceTabs` wrapper for a sibling to share.
- **R8c** `openLinkText(base, "", "split")` — PASS. Note opens in a new split; container stays in its current position.
- **R8d** Synthetic HTML5 drop onto `.anvil-proto-container` — PASS. Container has no drop handler; event absorbed silently, nothing lands in the container DOM.
- **R8e** Explicit `leaf.setViewState({type:"markdown"})` — PASS (regression-pin). The container is replaced as documented; `view.navigation = false` does not intercept an explicit `setViewState` call. See [third-party-plugin-compatibility.md](../explanations/third-party-plugin-compatibility.md).

The AC6 bite-check decomposed which mitigation carries which probe:

- **Placement** (`createLeafInParent(rootSplit, ...)`) carries R8b, R8c, R8d. The original prototype used `workspace.getLeaf("split", "horizontal")`, which put the container inside a new `WorkspaceTabs`, and R8b went red (sibling-into failure). Swapping to `createLeafInParent` turned R8b green.
- **`view.navigation = false`** carries R8a. Flipping to `true` with placement intact turns R8a red.
- **`setPinned(true)`** was tried as belt-and-suspenders and proven redundant — removing it with `navigation = false` in place left all five probes green. Dropped from the final design.

Tests live at `specs/anvil/pane-chrome-and-picker/phase-2-prototype/r8.e2e.ts`. Run with `npm run test:e2e:proto` (prototype must be built first — see its `README.md`). Part 2 spec: `specs/anvil/pane-chrome-and-picker/phase-2-workspace-container-part-2-spec.md`.
